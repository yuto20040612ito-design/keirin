# keirin

競輪の期待値評価のためのデータベースと収集基盤。

目的は「よく当たる予想」ではなく、**長期回収率が100%を超える賭けだけを選別できる状態**を作ること。
控除率が約25%あるため、市場（オッズ）より33%以上うまく確率を推定できなければ勝てない。

- 戦略と検証プロトコル: [`docs/STRATEGY.md`](docs/STRATEGY.md)
- データソース調査結果（robots.txt / API仕様）: [`docs/DATA_SOURCES.md`](docs/DATA_SOURCES.md)
- スキーマ定義: [`sql/schema.sql`](sql/schema.sql)

## いちばん重要なこと

**オッズの時系列収集を今日から動かすこと。**

レース結果や出走表は後からいくらでも遡れる。
だが**締切前オッズの履歴はどこにも売っていない。取り逃したら永久に手に入らない。**

「自分の予測 vs 市場」の差＝妙味を測るには締切直前オッズが必須で、
前日オッズでバックテストすると実際には買えない価格で幻の利益が出る。

したがってモデルを1行も書く前に、まず収集を回す。

```bash
python -m keirin.collect watch
```

これを止めないことが Phase 0 の唯一の仕事。

## セットアップ

収集だけなら Python 3.11+ 以外に何も要らない（標準ライブラリのみで動く）。
何ヶ月も回り続けるプロセスなので、依存で壊れるリスクを持ち込んでいない。

```bash
# 収集のみ
export PYTHONPATH=src

# DuckDB への投入・分析もする場合
pip install -e '.[analysis]'
```

## 使い方

```bash
# 年間の開催カレンダーを取得（1リクエストで年間分）
python -m keirin.collect calendar --year 2026

# ある日のレース一覧と締切時刻を確認
python -m keirin.collect plan --date 20260811

# 収集本体。締切前オッズを刻んで貯め続ける
python -m keirin.collect watch

# 確定した結果・払戻をバックフィル
python -m keirin.collect results --date 20260811

# 過去データをまとめて収集 (Phase 1)。中断しても同じコマンドで再開できる
python -m keirin.collect backfill --from 20260101 --to 20260811

# raw -> DuckDB
python -m keirin.load --data-root data --db data/keirin.duckdb

# ベースラインを市場と比較する (Phase 2)
python -m keirin.baseline --db data/keirin.duckdb
```

### 常駐させる

`watch` は日付が変わると当日の開催を自動で読み直すので、
起動しっぱなしにしておけばよい。systemd ユニットを
[`deploy/keirin-collect.service`](deploy/keirin-collect.service) に置いてある。

```bash
sudo cp deploy/keirin-collect.service /etc/systemd/system/
sudo systemctl enable --now keirin-collect
journalctl -u keirin-collect -f
```

### バックフィルの所要時間

1レースあたり4リクエスト（出走・ライン・オッズ・結果）。
全場だと1日およそ80レースなので、1.5秒間隔で**1日分に約8分**かかる。
1年分なら数十時間の連続作業になる。

夜間に流し続ける前提で、いつ止めても続きから再開できるようにしてある。
収集済みのキーは `data/manifest/` に記録され、再実行時はスキップされる。
索引を壊した場合は raw から作り直せる:

```bash
python -m keirin.collect rebuild-manifest
```

`--kinds` で対象を絞れる。まず結果とオッズだけ集めたいなら:

```bash
python -m keirin.collect backfill --from 20260101 --to 20260811 \
    --kinds AplRaceOdds,result_html
```

**過去レースのオッズは確定オッズ1点のみ**で、締切前の推移は遡れない。
推移が欲しければ `watch` を今日から回すしかない。

### オッズを刻む間隔

締切の 3600/2700/1800/1200/900/600/420/300/240/180/120/90/60/40/25/15 秒前と、
締切20秒後に取得する。締切直前ほど密なのは、**実際に買えるのは締切直前の価格**だから。

`official_dt`（オッズの公式時刻）が前回と同じなら保存しない。
市場が動いていないのに行だけ増やしてもディスクを食うだけで情報が増えない。

## データ構造

```
data/raw/<api_class>/dt=<YYYYMMDD>/part.jsonl.gz   ← 生レスポンス。不変・追記のみ
data/keirin.duckdb                                  ← 正規化テーブル。raw から再構築可能
```

**Raw 層は必ず残すこと。** パース仕様は必ず後で変えたくなる。
生データさえあれば作り直せるが、正規化済みだけ持つと後から項目を足せない。
再取得できないオッズでは致命的になる。

主要テーブル:

| テーブル | 内容 |
|---|---|
| `races` | 開催日, 場, R番号, 距離, 車立, **締切時刻**, 天候, グレード |
| `entries` | 車番, 枠番, 選手, 級班, **競走得点**, 脚質, ギヤ倍数, 決まり手内訳 |
| `race_lines` | **ライン構成**（ライン番号 × ライン内位置 × 車番） |
| `odds_snapshots` | 賭式 × 組番 × **official_dt** のオッズ時系列 |
| `results` | 着順, 着差, 上りタイム, **決まり手**, S/B |
| `payouts` | 全賭式の確定払戻・人気 |

### 判断に使うオッズと精算に使うオッズは別物

混同すると回収率を誤るので、ビューを分けてある。

| ビュー | 中身 | 使いどころ |
|---|---|---|
| `decision_odds` | 締切前に実際に見られた最後のオッズ | モデルの市場特徴量・購入判断 |
| `final_odds` | 確定オッズ（無ければ最後のスナップショット） | 回収率の計算 |

パリミュチュエルなので、いつ買っても受け取る価格は最終プールで決まる＝`final_odds`。
一方で買うかどうかを決める時点で見えているのは `decision_odds` まで。
**判断は `decision_odds`、精算は `final_odds`。逆にすると幻の利益が出る。**

### データが正しいかの確認方法

オッズが全組番そろっていれば `1/Σ(1/オッズ)` が払戻率（約75%）になる。
組番が欠けても重複しても、この値がずれる。取り込み後の健全性チェックに使える。

```sql
SELECT bet_type, round(avg(1.0/inv)*100, 1) AS payback_pct
FROM (SELECT race_id, bet_type, sum(1.0/odds_low) AS inv
      FROM final_odds WHERE odds_low IS NOT NULL AND bet_type <> 7
      GROUP BY 1, 2)
GROUP BY 1;
```

実測値（20260810 の59レース）: 2車複 73.9% / 2車単 74.4% / 3連複 74.4% / 3連単 74.8%。

## 収集マナー

- リクエスト間隔は**最低1.5秒**（`NetkeirinClient` がプロセス内でグローバルに直列化）
- 失敗時は指数バックオフでリトライし、諦めたら次へ進む（収集を止めない）
- 収集元は robots.txt で許可されている netkeirin のみ。
  公式 keirin.jp はレースデータページを robots.txt で拒否しているため使わない
  （選手マスタとバンク諸元は許可パスから取得可）

ブロックされて収集が止まることが最大の損失なので、速度より継続性を優先している。

### Phase 2 で見る数字

競輪には単勝が無いので、市場の1着確率は 2車単を2着側で周辺化して作る
（`P(i が1着) = Σ_j P(i→j)`、1/オッズを全組で正規化して控除率を落とす）。

モデルは条件付きロジット。レース内で1人だけが勝つので、独立な二値分類だと
レース内の確率合計が1にならず理論的に誤りになる。

`baseline` は一様分布・ベースライン・市場の log loss を並べ、
「ベースライン − 市場」の差をブートストラップで区間推定する。
**ベースラインが市場に有意に勝ってしまった場合は、まずリークを疑うこと。**
競走得点だけで市場超えは考えにくいので、その旨を出力にも書いてある。

666レース（検証220レース）での実測:

| | log loss | top1 |
|---|---|---|
| 一様分布 | 1.9777 | 25.0% |
| 競走得点のみ | 1.7019 | 35.9% |
| ＋ライン・展開 | **1.6237** | **40.5%** |
| 市場 | 1.3701 | 48.2% |

ライン特徴量による改善は +0.0781（95%CI +0.0130〜+0.1368）で有意。
市場との差は 0.3318 → 0.2536 に縮んだが、まだ有意に負けている。

ライン内位置は競輪では脚質の代理変数になる（先頭＝先行、番手＝追込）。
実際の勝率は3人ラインで 1番手24.5% / 2番手23.2% / **3番手2.3%** と、
**先頭と番手はほぼ互角で3番手だけが壊滅的**という構造になっている。
詳細は [`docs/STRATEGY.md`](docs/STRATEGY.md)。
